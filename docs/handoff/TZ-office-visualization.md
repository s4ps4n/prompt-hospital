# ТЗ: визуализация «Офис оркестратора» в стиле Theme Hospital

## 1. Контекст и цель

У нас есть ИИ-оркестратор — Гермес (координатор) и команда моделей-исполнителей (Claude Code,
GPT, Gemini и др.), каждая со своей ролью. Нужна **живая визуализация команды как офиса**:
пользователь открывает веб-страницу и видит, кто из моделей чем занят, что выполнено, что
блокировано.

Но это не просто картинка. Это **единый интерфейс управления оркестратором**, совмещающий
три вещи:

1. **Визуализацию работы** — кто из моделей чем занят, что выполнено, что блокировано.
2. **Приоритизацию задач** — задачам задаётся приоритет, очереди сортируются по нему.
3. **Управление составом моделей** — добавлять новые модели в офис и убирать свободные.

Через офис можно назначать задачи моделям, менять им роли, двигать приоритеты и добавлять
модели — и эти действия реально меняют состояние команды, а не только рисунок.

Задача — **мультяшный изометрический офис** в узнаваемом стиле игры Theme Hospital (Bullfrog,
1997). Не абстрактная «доска задач», а именно офис: комнаты, персонажи за столами, мебель.

## 2. Стиль — строго Theme Hospital / Bullfrog

Ориентир — скриншоты Theme Hospital. Ключевые признаки, которые обязательны:

- **Изометрия 2:1** (диметрия, угол ~26.5°) — как в игре.
- **Толстый тёмный контур** у всех объектов. Не чёрный, а тёплый тёмно-коричневый (~#241a0c).
- **Чиби-персонажи**: крупная голова (≈40–50% роста), маленькое тело, короткие ноги.
  Выразительные лица: белые глаза с зрачками, брови, улыбка, румянец.
- **Яркая сочная палитра**: цветные ковры в комнатах, светлые тёплые стены, контрастная одежда.
- **Ретро-мебель**: ЭЛТ-мониторы (не плоские), деревянные столы, кресла, растения в кадках.
- **Жёсткие тени**-эллипсы под персонажами и мебелью.
- Жёлтые вывески с именем над каждой комнатой.

Если стиль получается «плоский дашборд», а не «игра Bullfrog» — это не принято.

## 3. Состав сцены

Один этаж. Сверху/слева — **кабинет руководителя** (2×2 комнаты), остальные — кабинеты 1×1.

**8 персонажей-моделей** (имя, провайдер, роль, фирменный цвет):

| Персонаж | Провайдер | Роль | Цвет (волосы/одежда) |
|---|---|---|---|
| Гермес | DeepSeek | координатор | бирюза #3cc8dc / #0fa0be |
| Claude | Anthropic | исполнитель | рыжий #e09060 / #d07040 |
| GPT-5 | OpenAI | архитектор | зелёный #5fbf8a / #3f9f6a |
| Gemini | Google | фулстак | синий #7aa0e8 / #4a74c8 |
| Qwen | Alibaba | сисадмин | фиолетовый #b080e8 / #8a58c8 |
| Mistral | Mistral AI | дизайнер | янтарный #e8b060 / #c88830 |
| Grok | xAI | UX/UI | серо-бирюзовый #8fb8c0 / #5f8f98 |
| Llama | Meta | приёмщик | серый #b0bcc8 / #7f8f9f |

Каждый — за своим столом с ЭЛТ-монитором. У комнаты — жёлтая вывеска с именем и ролью.

**Детали фона:** растения по углам, кофемашина, ковры-акценты на полу.

**Это стартовый состав, не предел.** Число персон может быть любым — пользователь добавляет
модели (§5.5), и офис растёт. **Раскладка динамическая:** комнаты расставляются по сетке
автоматически из числа `workers`, а не нарисованы жёстко под 8. Добавили 9-ю модель — появилась
новая комната; заполнился ряд — вырос новый ряд или крыло этажа.

**Модель ≠ персонаж.** Одна и та же модель может быть представлена в офисе несколько раз —
с разными ролями (например, Claude Code как «исполнитель» и Claude Code как «архитектор» —
два персонажа с одинаковым лицом, но разными табличками ролей). Единица офиса — это
**пара «модель + роль»**, а не модель сама по себе.

## 4. Статусы и их визуализация

4 состояния, видны сразу, без чтения текста:

| Статус | Визуал | Анимация |
|---|---|---|
| **в работе** | экран светится синим | печатает (руки), голова кивает, экран пульсирует |
| **выполнено** | экран зелёный | спокоен |
| **блокировано** | экран тёмно-красный | красная лампочка мигает над головой |
| **ожидает** | экран тёмный | лёгкое покачивание |

Статус продублирован цветной лампочкой на вывеске.

## 5. Интерактивность — главный смысл

Офис — это управление, а не наблюдение. Три взаимодействия обязательны:

### 5.1 Перетаскивание задачи (drag-and-drop)

- **Кабинет Гермеса — источник задач.** У него на столе лежит «стопка задач» (очередь):
  карточки-конверты, которые можно взять.
- Пользователь **перетаскивает задачу из кабинета Гермеса на комнату модели** → задача
  назначена этой модели.
- Визуально: конверт «летит» по офису в комнату, персонаж переходит в «в работе» и начинает
  печатать, на вывеске появляется название задачи.
- **Обратное:** можно забрать задачу у модели (перетащить конверт обратно в очередь Гермеса
  или на другую модель) → персонаж возвращается в «ожидает».
- **Перетаскивание на занятую модель → очередь.** Задача не вытесняет текущую и не получает
  отказ: она встаёт второй/третьей в очередь к этой модели. Визуально — на столе модели
  помещается несколько конвертов (текущая задача + очередь), персонаж продолжает печатать.

### 5.2 Смена роли модели

- Клик по персонажу → открывается карточка с полем «роль».
- Роль выбирается из **фиксированного списка**: исполнитель, архитектор, фулстак, сисадмин,
  дизайнер, UX/UI, приёмщик (плюс «координатор» — только у Гермеса). Свободного ввода нет.
- Роль меняет **подпись на вывеске** и, при желании, цвет/значок комнаты.
- Роль хранится в журнале и влияет на то, какие задачи модели доступны для перетаскивания.
- **Смена роли занятой модели → отказ.** Если модель сейчас «в работе», сменить роль нельзя:
  поле блокируется, при попытке — подсветка «нельзя» и пояснение «сначала заверши/сними
  задачу». Менять роль можно только когда модель свободна (статус «ожидает» или «выполнено»).

### 5.2а Добавить ту же модель с другой ролью

- Отдельное действие: **«добавить экземпляр модели»**. Пользователь выбирает модель (например,
  Claude) и роль — в офисе появляется **вторая комната** с тем же лицом, но другой ролью.
- Так одна модель ведёт две роли параллельно, каждая со своей очередью задач и своим статусом.
- Это не смена роли существующего персонажа, а создание нового рабочего места.

### 5.3 Карточка персонажа (клик)

По клику — панель с деталями модели: имя, провайдер, роль (редактируемая), текущая задача,
счётчик выполненных, история последних задач. Панель не перекрывает сцену, открывается рядом.

### 5.4 Приоритизация задач

- У каждой задачи есть **приоритет**: высокий / средний / низкий (в данных — число 3/2/1).
- **Очередь Гермеса и очередь каждой модели сортируются по приоритету** — высокий всегда сверху.
- Смена приоритета: в стопке конвертов перетащить задачу выше/ниже (или кнопки ↑↓ в карточке
  задачи, или выбор приоритета в карточке). После смены очередь пересортировывается.
- Визуально: у конверта **цветной флажок** — красный = высокий, жёлтый = средний, серый = низкий.
- Когда задача назначена модели, её приоритет определяет порядок в очереди этой модели.

### 5.5 Добавление моделей

- Действие **«добавить модель»** → открывается **каталог доступных моделей** с провайдерами
  (Claude/Anthropic, GPT/OpenAI, Gemini/Google, Qwen/Alibaba, Mistral/Mistral AI, Grok/xAI,
  Llama/Meta, DeepSeek и др.).
- Выбрал модель + роль → в офисе появляется **новая комната** с персонажем, готовым принимать
  задачи (статус «ожидает»).
- **Куда ставится новая комната:** в ближайшую свободную ячейку сетки; при заполнении ряда
  добавляется новый ряд/крыло. Раскладка пересчитывается автоматически из числа `workers`,
  ничего не «переползает» вручную.
- **Убрать модель** можно только свободную (без задач в работе и без очереди) — иначе отказ.
  Комната освобождается, раскладка снова пересчитывается.

## 6. Журнал оркестратора — источник истины

Всё, что нарисовано и чем управляют — читается/пишется в **журнал** (JSON-структура). Офис —
только интерфейс поверх него.

Минимальная структура:

```json
{
  "workers": [
    {"id":"w1", "model":"claude", "name":"Claude Code", "provider":"Anthropic",
     "role":"исполнитель", "color":"#d07040", "status":"run", "task":null},
    {"id":"w2", "model":"claude", "name":"Claude Code", "provider":"Anthropic",
     "role":"архитектор", "color":"#d07040", "status":"wait", "task":null}
  ],
  "catalog": [
    {"model":"claude",   "name":"Claude Code", "provider":"Anthropic", "color":"#d07040"},
    {"model":"gpt5",     "name":"GPT-5",       "provider":"OpenAI",   "color":"#3f9f6a"}
  ],
  "queue": [
    {"id":"T-12", "title":"починить смоук karkas", "status":"wait",
     "priority":3, "assignedTo":null}
  ],
  "operations": {
    "assign":      {"task":"T-12", "worker":"w1"},
    "reassign":    {"task":"T-12", "from":"w1", "to":"w2"},
    "unassign":    {"task":"T-12"},
    "setRole":     {"worker":"w1", "role":"архитектор"},
    "setPriority": {"task":"T-12", "priority":2},
    "addWorker":   {"model":"claude", "role":"сисадмин"},
    "removeWorker":{"worker":"w1"}
  }
}
```

- Единица — **worker** (рабочее место). Одна модель (`model`) может дать несколько worker'ов
  с разными ролями (`w1` и `w2` — оба Claude, но «исполнитель» и «архитектор»).
- `catalog` — доступные модели для добавления; `priority` (3/2/1) — приоритет задачи.
- Перетащил задачу → `assign`. Сменил роль → `setRole`. Добавил экземпляр модели → `addWorker`.
  Поменял приоритет → `setPriority`. Убрал свободную модель → `removeWorker`.
- Сортировка очередей по приоритету — производная от состояния, считается при отрисовке.
- Отрисовка и анимация — чистые функции от состояния журнала. Нет «состояния в DOM».
- Для прототипа журнал можно держать в памяти + localStorage; для боевого — это уже API
  оркестратора (выходит за рамки данной задачи, но структура обязана быть совместимой).

## 7. Технические требования

- **Самодостаточный файл** (или набор файлов) — открывается оффлайн, без сборки, без CDN.
- SVG + CSS-анимация (SMIL или keyframes). Никаких внешних библиотек.
- **Данные и операции отделены от отрисовки** (см. §6). Drag-and-drop и смена роли меняют
  состояние журнала, а не напрямую DOM.
- Drag-and-drop работает мышью и, где возможно, тачем.
- Адаптив: на узком экране сцена масштабируется, не ломается.
- Кроссбраузерно: Chrome/Firefox/Safari, свежие версии.

## 8. Критерии приёмки

- Открываешь страницу → узнаётся Theme Hospital по стилю (не «похоже на что-то», а именно он).
- Все 8 персонажей различимы по цвету и подписаны.
- 4 статуса различаются с первого взгляда, анимация плавная.
- **Перетаскивание:** взял задачу из очереди Гермеса → бросил на Claude → Claude начал
  печатать, на его вывеске появилась задача. Забрал обратно → вернулся в «ожидает».
- **На занятую модель:** перетащил задачу на занятого Claude → задача встала второй в его
  очередь (на столе два конверта), текущая задача не прервалась.
- **Смена роли:** клик по свободному персонажу → сменил роль → вывеска обновилась. У занятого
  персонажа поле роли заблокировано.
- **Добавление модели:** «добавить модель» → выбрал Gemini + «сисадмин» → появилась новая
  комната. Убрать свободную модель — можно, занятую — отказ.
- **Приоритет:** в очереди задачи с высоким приоритетом выше. Перетащил задачу выше/ниже →
  порядок пересортировался, флажок изменил цвет.
- Действия не теряются при обновлении страницы (localStorage).
- Нет разъехавшихся объектов, наложений, битого текста, ошибок консоли.

## 9. Границы (чего НЕ делать)

- Не делать 3D-модели (Three.js/WebGL) — нужен плоский изометрический спрайтовый вид.
- Не привязываться к реальному имени продукта в самой картинке (название офиса — нейтрально).
- Не рисовать «реалистичных» персонажей — только мультяшные чиби.
- Не подключать реальный оркестратор/API в этой итерации — только локальный журнал + localStorage.

## 10. Что уже есть

Есть рабочая заготовка (SVG-изометрия + чиби-персонажи + анимация), но она **не дотягивает
до стиля** — автор (текстовая модель) не видит результат и не может попасть в визуальный
референс. Заготовку можно взять как каркас координат и структуры данных, но визуал
переделать заново. Интерактива (drag-and-drop, смена роли) в заготовке пока нет.
