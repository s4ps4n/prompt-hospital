**Критично**

1. **Файл: `ops.ts`, функция `detach`**  
   **Суть:** При снятии задачи с модели (`detach`) функция не обновляет статус модели на `wait`, если у неё больше нет задач. Это нарушает инвариант: `task == null` должен быть эквивалентен статусу `wait` (или `done` после завершения).  
   **Почему:** В `detach` после `t.assignedTo = null` вызывается `takeNext(j, w, 'wait')` **только если** `w.task === t.id`. Если задача была в очереди (не текущая), то `w.task !== t.id`, и `takeNext` не вызывается → статус модели остаётся прежним (`run` или `blocked`), несмотря на то, что она больше не имеет назначенных задач в работе.  
   **Как исправить:** После снятия задачи всегда проверять, есть ли у модели текущая задача. Если нет — установить статус в `wait` (или `done`, если только что завершено, но это обрабатывается в `complete`).  
   ```ts
   function detach(j: Journal, t: Task): void {
     if (!t.assignedTo) return
     const w = findWorker(j, t.assignedTo)
     t.assignedTo = null
     if (w && w.task === t.id) {
       takeNext(j, w, 'wait')
     } else if (w && !w.task) {
       // Задача была в очереди, а текущей нет → модель простаивает
       w.status = 'wait'
     }
   }
   ```

2. **Файл: `ops.ts`, функция `complete`**  
   **Суть:** После завершения задачи модель переходит в статус `done` через `takeNext(j, w, 'done')`, но инвариант требует, чтобы `task == null` ⇔ статус ∈ {`wait`, `done`}. Однако в текущей реализации статус `done` не обрабатывается как "свободен для новой задачи" — модель не может взять новую задачу, пока не будет явно разблокирована или переведена в `wait`.  
   **Почему:** В `takeNext` при `idleStatus: 'done'` статус устанавливается в `done`, но нет механизма автоматического перехода из `done` в `wait`. Это приводит к тому, что модель "застревает" в `done` и не может взять новую задачу из очереди, даже если она есть.  
   **Как исправить:** После завершения задачи модель должна переходить в `wait`, а не `done`, если она готова к новой работе. Или ввести логику, при которой `done` — это финальное состояние, и модель не участвует в очереди. Но по инварианту и логике (`takeNext` с `'done'`) предполагается, что после `done` модель может продолжить работу.  
   **Лучшее решение:** Изменить `takeNext` в `complete` на использование `'wait'`, а не `'done'`, так как завершение задачи — это не финал работы модели, а переход к следующей.  
   ```ts
   // В complete:
   const next = takeNext(j, w, 'wait') // вместо 'done'
   ```
   И оставить `takeNext(j, w, 'done')` только если нужно фиксировать завершение смены — но это не требуется по инварианту.

3. **Файл: `ops.ts`, функция `block`**  
   **Суть:** При блокировке модели (`blocked`) задача остаётся текущей (`w.task` не меняется), но инвариант требует, чтобы при статусе `blocked` задача была не `null` (что соблюдается), однако при разблокировке (`blocked` → `run`) не проверяется, актуальна ли задача (например, не была ли она снята другим способом).  
   **Почему:** Хотя в `block` есть проверка `if (!w || !w.task)`, после разблокировки статус становится `run`, но если задача была снята во время блокировки (например, через `unassign` или `reassign` от другого работника), то модель останется с `task: TaskId | null` (не `null`), но задача больше не в очереди → нарушение ссылочной целостности.  
   **Как исправить:** После изменения статуса в `block` проверять, существует ли задача и всё ещё назначена ли она этой модели.  
   ```ts
   const block: Mutator<'block'> = (j, a) => {
     const w = findWorker(j, a.worker)
     if (!w || !w.task) return { err: 'Блокировать можно только задачу в работе' }
     const t = findTask(j, w.task)
     if (!t || t.assignedTo !== w.id) {
       return { err: `Задача ${w.task} больше не назначена этой модели` }
     }
     w.status = w.status === 'blocked' ? 'run' : 'blocked'
     return { msg: `${w.name}: ${w.status === 'blocked' ? 'блокировано' : 'снова в работе'}` }
   }
   ```

**Средне**

4. **Файл: `ops.ts`, функция `reorder`**  
   **Суть:** При перестановке задачи перед другой (`t.order = b.order - 0.5`) используется дробное значение для `order`, а затем вызывается `renumber`, который присваивает целые числа. Однако если несколько операций `reorder` выполняются подряд без вызова `renumber` (например, в рамках одной транзакции, но каждая операция — отдельная), то дробные значения накапливаются и могут привести к потере точности или некорректной сортировке.  
   **Почему:** Хотя каждая операция оборачивается в `pure` и работает с копией журнала, внутри одной операции после `t.order = b.order - 0.5` сразу вызывается `renumber(j)`, который преобразует все `order` в целые. Так что в рамках одной операции проблема не проявляется.  
   **Однако:** Если бы `renumber` не вызывался внутри `reorder`, то да — были бы проблемы. Но он вызывается.  
   **Вывод:** Нарушений нет.  
   **Исправление:** Не требуется.  
   *(Примечание: при повторном взгляде — `renumber` вызывается в конце `reorder`, так что дробные значения не сохраняются. Ошибки нет.)*

5. **Файл: `ops.ts`, функция `assign`**  
   **Суть:** При назначении задачи свободной модели (`wasFree`) задаче присваивается `t.order = ++j.seq`, но эта задача становится текущей, а не попадает в очередь. Однако `order` используется только для сортировки в очередях и лотке. Для текущей задачи `order` не должен влиять на позицию, так как она вынесена из очереди.  
   **Почему:** Назначение `order` текущей задаче избыточно и может ввести в заблуждение, но не нарушает инварианты напрямую. Однако если позже эта задача будет снята и возвращена в очередь, её `order` будет основан на старом `seq`, что может привести к неожиданной позиции в очереди.  
   **Как исправить:** Не присваивать `order` при назначении на текущую позицию; оставлять его без изменений или сбрасывать при возврате в очередь.  
   ```ts
   // В assign:
   // t.order = ++j.seq   // УДАЛИТЬ ЭТУ СТРОКУ
   placeOnWorker(j, t, w)
   if (wasFree) {
     return { msg: `${t.id} → ${w.name} (${w.role}): в работе` }
   }
   // При возврате в очередь — order будет установлен в placeOnWorker? Нет.
   // Лучше: при placeOnWorker не трогать order, а при возврате в очередь (detach + последующая вставка) — устанавливать.
   ```
   Но в текущем коде `placeOnWorker` не меняет `order`, а `t.order = ++j.seq` выполняется до него.  
   **Решение:** Удалить строку `t.order = ++j.seq` из `assign`. При возврате задачи в очередь (например, через `unassign`) порядок будет установлен там через `t.order = ++j.seq`, что корректно.

6. **Файл: `ops.ts`, функция `setPriority`**  
   **Суть:** При изменении приоритета задачи, если она назначена модели, в сообщении говорится: `"очередь ${w.name} пересортирована"`, но фактически пересортировка происходит только при следующем вызове операций, которые используют `sort` (например, `workerQueue`, `trayTasks`). Однако журнал не изменяется напрямую — порядок задач в `j.queue` не меняется, только их `priority` и `order` (через `renumber` не вызывается).  
   **Почему:** В `setPriority` не вызывается `renumber(j)`, поэтому изменение приоритета не приводит к немедленной пересортировке очереди в журнале. Очередь останется в старом порядке до следующей операции, которая вызовет `sort` (например, `reorder`, `addTask`, `assign`).  
   **Как исправить:** Добавить вызов `renumber(j)` после изменения приоритета, если нужно гарантировать, что журнал отражает актуальный порядок немедленно.  
   ```ts
   t.priority = a.priority
   renumber(j) // ДОБАВИТЬ
   const w = t.assignedTo ? findWorker(j, t.assignedTo) : undefined
   // ...
   ```

**Мелочь**

7. **Файл: `ops.ts`, функция `reassign`**  
   **Суть:** Вызывает `assign(j, { task: a.task, worker: a.to })` напрямую, но `assign` — это `Mutator`, а не `Op`. Однако в контексте `pure` это допустимо, так как `reassign` сам является `Mutator`, и он вызывает другую `Mutator`-функцию над тем же черновиком.  
   **Почему:** Это не нарушает чистоты, потому что оба работают с одним `draft` (копией журнала).  
   **Вывод:** Нормально. Нет проблемы.

8. **Файл: `ops.ts`, функция `removeWorker`**  
   **Суть:** Проверка `if (w.task || workerQueue(j, w.id).length)` корректна, но `workerQueue` уже исключает текущую задачу, поэтому условие проверяет: есть ли текущая задача **или** есть задачи в очереди.  
   **Почему:** Это правильно — нельзя удалить работника, если у него есть любые назначенные задачи (текущие или в очереди).  
   **Вывод:** Корректно.

9. **Файл: `types.ts`, тип `LogEntry`**  
   **Суть:** Используется распределённый тип с ключами из `OpName`, но если в будущем добавятся новые операции, а `LogEntry` не будет обновлён — может возникнуть несоответствие.  
   **Почему:** Это не ошибка в текущем коде, а потенциальная уязвимость при поддержке.  
   **Как исправить:** Оставить как есть — это типобезопасно при условии, что `OpName` и `LogEntry` обновляются вместе.  
   **Вывод:** Не является ошибкой в текущем коде.

10. **Файл: `selectors.ts`, функция `currentTask`**  
    **Суть:** Возвращает задачу по `w.task`, но не проверяет, существует ли такая задача в `j.queue`.  
    **Почему:** Если задача была снята (например, через `unassign` от другой модели), но `w.task` не был обновлён (из-за бага в `detach`), то `currentTask` вернёт несуществующую задачу.  
    **Однако:** Это следствие бага в `detach` (пункт 1), а не独立问题.  
    **Вывод:** Не является первопричиной.

### Итоговый список по убыванию серьёзности:

**Критично**  
1. `ops.ts`: `detach` — не обновляет статус модели при снятии задачи из очереди → нарушение инварианта `task == null ⇔ status ∈ {wait, done}`.  
   **Исправление:** После `t.assignedTo = null` всегда проверять, если `w.task === null`, то установить `w.status = 'wait'`.  
2. `ops.ts`: `complete` — устанавливает статус модели в `done` после завершения, но модель не может взять новую задачу из очереди → нарушение ожидания, что `done` должно позволять переход к новой работе.  
   **Исправление:** В `takeNext(j, w, 'done')` заменить на `'wait'`, либо ввести отдельную логику для `done` как финального состояния (но по контексту логичнее `'wait'`).  
3. `ops.ts`: `block` — не проверяет, что задача всё ещё назначена модели после изменения статуса → риск работы с "висячей" задачей.  
   **Исправление:** После изменения статуса проверить, что `findTask(j, w.task)?.assignedTo === w.id`.

**Средне**  
4. `ops.ts`: `assign` — избыточно присваивает `order` текущей задаче, что может привести к некорректной позиции при возврате в очередь.  
   **Исправление:** Удалить строку `t.order = ++j.seq` в `assign`.  
5. `ops.ts`: `setPriority` — не вызывает `renumber`, поэтому изменение приоритета не отражается в порядке очереди немедленно.  
   **Исправление:** Добавить `renumber(j)` после изменения `t.priority`.

**Мелочь**  
6. `ops.ts`: `reassign` — вызывает `assign` напрямую как `Mutator` — корректно, так как оба работают с черновиком.  
   *(Нет проблемы — оставлено для полноты.)*  
7. `types.ts`: `LogEntry` — потенциальная несинхронность с `OpName` при расширении — но не ошибка в текущем коде.  
8. `selectors.ts`: `currentTask` — не проверяет существование задачи — но это следствие бага в `detach`, не независимая проблема.  

> **Примечание:** Все остальные части кода соответствуют инвариантам, типам и иммутабельности. Входной журнал не мутируется благодаря `structuredClone` в `pure`. Операции согласованы с логикой назначения/очереди.
