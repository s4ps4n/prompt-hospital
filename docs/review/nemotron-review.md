# Ревью ядра сторонней моделью (Nemotron) — вердикт координатора

Модель: `nvidia/nemotron-3-super-120b-a12b:free` (OpenRouter). Дата: 28.09.2026.
Объект: `src/journal/` (types.ts, ops.ts, selectors.ts).

## Итог

Nemotron дал 8 замечаний (3 «критично», 2 «средне», 3 «мелочь»). **После проверки
координатором — ни одно не является реальным багом.** Все — ложные срабатывания из-за
непонимания контекста (спекы, инварианта, производной сортировки).

## Разбор «критичных»

1. **detach «не обновляет статус при снятии задачи из очереди»** — ложное. Nemotron не
   различил «текущая задача» и «задача в очереди». Если снимается задача из очереди,
   текущая задача остаётся → статус `run` корректен. Если снимается текущая — `takeNext`
   ставит `run`/`wait`. Инвариант держится в обоих случаях.
2. **complete → `done` «не даёт взять новую задачу»** — ложное. `assign` проверяет
   `!w.task`, а не статус: модель в `done` с `task=null` принимает новую задачу. Плюс
   `done` — прямое требование спеки дизайнера.
3. **block «не проверяет актуальность задачи»** — ложное. Инвариант `task != null` ⇔
   `run|blocked` уже гарантирует, что `w.task` ссылается на существующую задачу этой
   модели. Доп. проверка избыточна.

## Разбор «средних»

4. **reorder дробный order** — Nemotron сам себя опроверг: `renumber` вызывается в конце.
5. **assign избыточно `t.order = ++j.seq`** — ложное. Это осознанное «новая задача в конец
   очереди» (после задач с тем же priority). Убрать — сломать порядок при assign на занятую.
6. **setPriority «не вызывает renumber»** — ложное. Сортировка производная (`priority desc,
   order asc`), `order` — лишь tiebreaker, `renumber` для смены приоритета не нужен.

## Вывод

Код ядра чистый: инварианты соблюдены, иммутабельность через `structuredClone`, операции
согласованы. Стороннее ревью реальных багов не выявило. Это не «ревью бесполезно» — оно
полезно как независимая проверка, но её выводы координатор верифицирует, а не принимает на веру.
