## Воспроизведённые пропуски SEO-пробы

Объект: `engine/deploy/lib/probe-seo.mjs`, экспорт `checkSeo`.
Это дефекты диагностического покрытия, а не доказательство, что витрина сейчас
генерирует испорченные данные.

1. **Некорректный `dateModified` принимается как корректный.** В JSON-LD передано
   `"dateModified":"not-a-date"`. Фактически `bad=[]`, `checked=1`.
   `hasDateModified` проверяет только тип string; не проверяет дату и принадлежность узла странице.
2. **Некорректный `lastmod` принимается как корректный.** В sitemap передано
   `<lastmod>garbage</lastmod>`. Фактически `bad=[]`, `checked=1`.
   `sitemapGaps` проверяет наличие непустого текста, но не корректность даты.
3. **Относительная ссылка остаётся непроверенной без ошибки.** `/llms.txt` содержит
   `- [Page](/about)`, sitemap — один адрес `/about`. Фактически `bad=[]`, `checked=0`.
   Парсер видит только абсолютные HTTP(S)-ссылки; защита от пустого списка действует
   лишь при числе адресов sitemap больше одного.

Воспроизведение без сети и БД:

```bash
node docs/review/seo-515/probe-regressions.mjs /home/hermes/engine-autopost/work/cms_teach/engine
```

[Сценарий](seo-515/probe-regressions.mjs) и [результат](seo-515/probe-regressions.log):
контроль корректных данных проходит, три проверки отклонения плохих данных падают.
Код возврата 1 ожидаем до исправления диагностического покрытия.

Дополнительно: реализация опрашивает максимум 40 товарных ссылок, остальные — выборочно
через равномерную выборку. Это явно закреплено отдельным тестом, но комментарий вверху
пробы и исходная запись #519 в changelog обещают проверку КАЖДОЙ ссылки. При приёмке
нужно сопоставить эту уступку с актуальным текстом задачи; полный обход товаров не доказан.
