# ТЗ: Интеграция Точка-банк → Битрикс24 (v3)

**Задача:** `T-71` · зона `b24-bank` · приоритет 1 · v3 от 30.09 — v2 архитектора + воронка и стадии из v4 команды

---

## Цель

Когда на расчётный счёт приходит оплата, соответствующий счёт в Битрикс24 автоматически переходит
в статус «оплачен» — **только при уверенном совпадении**; всё неоднозначное уходит человеку.

---

## Главное требование безопасности

**Банковские и персональные данные не покидают контур владельца.**

- **Не ставить** приложения из Маркетплейса B24 (First Open и подобные) — поток платежей идёт
  через сервер разработчика, это утечка банковской тайны.
- **Не отправлять** платёжные данные во внешние сервисы и LLM-шлюзы (включая Jev через
  `ag.omni.mice.zone`).
- **Матчинг** — только локальная арифметика.
- **Что сервис хранит** — ровно одно: журнал идемпотентности (§6). Ничего больше: ни сумм, ни
  ИНН, ни назначений, ни выписок, ни остатков.
- **В логах** — без номеров счетов, назначений, сумм и ИНН.
- **Битрикс24 — контур владельца.** Туда писать суммы и ИНН можно и нужно (иначе бухгалтер не
  разберёт неоднозначные платежи); это его данные в его системе.

---

## Архитектура

```
Точка (вебхук о поступлении, POST + JWT)
      ↓
Слушатель на сервере владельца (HTTPS за Traefik):
  1. проверка подписи JWT по JWKS Точки (iss, aud, exp) → не прошла → 401, ничего не делаем
  2. ответ 200 сразу (Точка повторяет вебхук, если ответ не пришёл быстро)
  3. в очередь → обработка после ответа
      ↓
Матчинг со счетами B24 (§4) — данные платежа в памяти, не сохраняются
      ↓
Обновление счёта / пометка / задача в B24 через локальное приложение (§5)
      ↓
Запись в журнал идемпотентности (§6): id платежа, id счёта, результат, время

Раз в сутки: сверка за 24 часа через API Точки (§7) — тот же матчинг, без сохранения выписки.
```

**Точка — единственный внешний контур.** Никаких посредников.

---

## 1. Вебхук Точки

- Подписка на событие поступления средств для `account_id` владельца (право `ManageWebhookData`).
- **Подпись:** JWT проверяется по публичному ключу из JWKS Точки, кэш ключей — час, сверяются
  `iss`, `aud`, `exp`. Любой POST без валидной подписи → 401, в лог — только «отклонён, подпись».
- **Быстрый ответ:** 200 до обработки; обработка — в очереди (in-process, персистить не надо: если
  процесс упал — сверка §7 подберёт).
- **Повторы:** один и тот же платёж может прийти дважды — гасится журналом идемпотентности (§6)
  по `operationId` Точки.
- Ограничить приём по IP-диапазонам Точки, если она их публикует; если нет — подпись достаточна.

## 2. Данные платежа, которые используются (одноразово, в памяти)

`operationId`, сумма, ИНН плательщика (может отсутствовать — физлица, самозанятые, переводы по
СБП), назначение, дата. После обработки — не сохраняются.

## 3. Счета и ИНН в Битрикс24

- **Тип счетов уточнить у владельца до старта:** старые `crm.invoice` или смарт-процесс «Счета»
  (`crm.item`, `entityTypeId 31`, актуальный вариант с 2022 г.). Дальше по тексту — смарт-процесс;
  для старых счетов — те же шаги другими методами.
- **Стадия «оплачен»** — `stageId` у каждого портала свой (вида `DT31_1:P`). Записать в конфиг
  после чтения списка стадий (`crm.status.list` / стадии смарт-процесса), не хардкодить.
- **Кандидаты** — счета в четырёх стадиях поиска (§3а) с точной суммой; кэш списка — минута.
- **ИНН** — не у счёта: цепочка счёт → компания/контакт → реквизиты (`crm.requisite.list`,
  поле `RQ_INN`). Кэш «компания → ИНН» — сутки.
- При закрытии — стадия «оплачен» + дата оплаты + комментарий в таймлайн «оплачен автоматически
  по платежу <operationId>».

## 3а. Воронка счетов — как есть у владельца

| # | Стадия | Кто ставит |
| --- | --- | --- |
| 1 | Новый | — |
| 2 | Авто ООО: отправка, счёт и акт | робот |
| 3 | Авто ИП | робот |
| 4 | Клиент прочитал ⚠️ | робот |
| 5 | Платёж просрочен | робот B24 (правило 5 дней) |
| 6 | Сомнения | человек |
| 7 | Не оплачен | человек вручную |
| 8 | **Оплачен** | **наша система** |

Стадии «Провален» нет. «Платёж просрочен» — не финал, а шаг воронки.
**Задача системы — найти счёт по платежу и перевести в «Оплачен». Больше ничего не менять.**

**Где ищем:** только стадии 2, 3, 4, 5 — весь путь «счёт отправлен, ждём деньги».
**Не ищем:** Новый (не отправлен), Сомнения и Не оплачен (решено человеком), Оплачен (закрыт).

**Привязка по `STATUS_ID`, не по названию.** Названия стадий правят в интерфейсе, `STATUS_ID`
стабилен; привязка к названию сломает интеграцию молча. В конфиг — `STATUS_ID` четырёх стадий
поиска, `STATUS_ID` стадии «Оплачен», `entityId` воронки (`SMART_INVOICE` или `INVOICE` — уточнить
через `crm.status.list`).

**Роботы B24** сами переводят в «Платёж просрочен» через 5 дней — свою логику по срокам не
дублировать; наша система стадии кроме «Оплачен» не трогает.

## 4. Правила сопоставления

Сигналы по убыванию надёжности: **1) ИНН плательщика, 2) сумма (точно, до копейки),
3) назначение** — вспомогательное: нет или неверное — работаем без него.

| Уровень | Условие | Действие |
| --- | --- | --- |
| **1 — уверенно** | ИНН + сумма совпали ровно с **одним** счётом из стадий 2–5 | закрыть автоматически |
| **2 — неоднозначно** | несколько счетов с таким ИНН и суммой; или ИНН есть, но сумма не совпадает ни с одним; или сумма равна сумме двух+ счетов этого ИНН; частичная оплата; переплата | **ничего не менять**; комментарий в таймлайн каждого счёта-кандидата: сумма платежа, ИНН, дата, список кандидатов и **какой именно случай** (несколько/частичная/переплата/сумма двух) |
| **3 — не разобрано** | ИНН отсутствует **и** сумма не совпадает ни с одним счётом; или ИНН есть, но у него нет неоплаченных счетов | задача в B24 на ответственного за счета: сумма, ИНН (если есть), назначение, дата, `operationId`; срок — сегодня |

- ИНН нет, но сумма совпала ровно с одним счётом — **уровень 2**, не 1: сумма без ИНН —
  недостаточный сигнал (два клиента по 15 000 ₽ — обычное дело).
- **Автозакрытие — только уровень 1.** Любое сомнение — человеку. Это защита от молчаливого
  закрытия не того счёта.

## 5. Доступ в Битрикс24 — локальное приложение, не входящий вебхук

Входящий вебхук — это токен с правами на всю CRM в нашем конфиге; утечка = чужой доступ ко всей
CRM. Поэтому: **локальное приложение** портала с OAuth и правами только на смарт-процесс счетов,
реквизиты, таймлайн и задачи. Токены — в env на сервере владельца, не в коде и не в git; ротация
раз в квартал; refresh-token обновляется автоматически.

## 6. Журнал идемпотентности — единственное хранилище

Таблица/файл: `operationId` · `invoiceId` (или пусто) · `result` (closed / review / unresolved /
rejected) · `at`. **Без сумм, ИНН, назначений.** Срок хранения 90 дней, старше — удаляется.
Повторный вебхук или сверка с уже известным `operationId` — пропуск без действий.

## 7. Сверка раз в сутки

Вебхуки теряются (Точка недоступна, наш процесс перезапускался). Раз в сутки — запрос
операций по счёту за последние 24 часа через API Точки, каждая — через тот же матчинг и журнал
(§6): что уже обработано — пропускается, что пропущено — обрабатывается. **Выписка не
сохраняется.** Плюс проверка, что подписка на вебхук у Точки активна (список вебхуков) — если
нет, переподписаться и уведомить.

## 8. Уведомления

- Уровень 1 — ничего (комментарий в таймлайне достаточно).
- Уровень 2 и 3 — задача/комментарий в B24 (§4) + одно сообщение ответственному в чат B24
  (не в Telegram и не наружу).
- Сбои интеграции (подпись не проходит подряд, Точка недоступна, токен B24 протух) — сообщение
  ответственному в B24 и запись в лог без данных платежей.

---

## Данные, нужные от владельца

1. Токен API Точки (JWT) и `account_id` расчётного счёта; право `ManageWebhookData`.
2. Локальное приложение в Битрикс24 (client_id/secret) с правами на счета, реквизиты, таймлайн,
   задачи — создаётся владельцем портала, мы даём список прав.
3. `STATUS_ID` стадий 2–5 и «Оплачен», `entityId` воронки — снять через `crm.status.list`; тип счетов (старые / смарт-процесс).
4. Ответственный за счета (кому задачи по уровням 2–3).
5. Подтверждение: у контрагентов стабильный ИНН в платежах; бывают ли два счёта на одну сумму у
   одного контрагента (если часто — уровень 2 будет частым, это ожидаемо).
6. Доступ к песочнице Точки и тестовому порталу B24 для приёмки до боя.

## Приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Платёж с уникальными ИНН + суммой | ровно один счёт из стадий 2–5 → «Оплачен» с датой и комментарием; другие не тронуты |
| Совпадение только со счётом в «Сомнения» / «Не оплачен» / «Новый» | не найден → уровень 3; стадии, решённые человеком, не трогаем |
| Стадию переименовали в интерфейсе | ничего не сломалось — привязка по `STATUS_ID` |
| Два счёта с таким ИНН и суммой | ни один не закрыт; в обоих таймлайнах пометка с указанием «несколько кандидатов» |
| Сумма без ИНН совпала с одним счётом | уровень 2, не закрыт |
| Сумма = сумме двух счетов контрагента | уровень 2 с пометкой «сумма двух» |
| Платёж без ИНН и без совпадений | задача в B24 ответственному с данными платежа |
| Повторный вебхук по тому же `operationId` | ничего не происходит (журнал §6) |
| POST без подписи / с чужой подписью | 401, ничего не изменилось, в логе «отклонён, подпись» |
| Пропущенный вебхук | сверка §7 на следующий день закрыла счёт (уровень 1) |
| Отозванная подписка на вебхук | сверка обнаружила, переподписалась, уведомила |
| Логи | без сумм, ИНН, номеров счетов, назначений |
| Хранилище сервиса | только журнал §6, записи старше 90 дней удалены |
| **Контроль-реверт** | убрать проверку уникальности → тест «два совпадения» красный; убрать проверку подписи → тест «чужая подпись» красный; убрать журнал → тест «повторный вебхук» красный |

Приёмка сначала на песочнице Точки и тестовом портале B24, затем неделя на бою в режиме
«только пометки» (уровень 1 тоже пишет в таймлайн, но не закрывает), потом включение автозакрытия.

---

## Чего не делать

- Не ставить сторонние приложения Маркетплейса.
- Не отправлять платёжные данные в LLM/Jev и любые внешние API.
- Не закрывать счёт при любой неоднозначности — лучше оставить человеку.
- Не хранить выписки, остатки, суммы, ИНН — ничего кроме журнала §6.
- Не использовать входящий вебхук B24 с правами на всю CRM.
- Не допускать «терпимость» по сумме (±1 ₽ и т. п.) — только точное совпадение.

## Оценка

2–3 дня разработки после получения данных от владельца; неделя наблюдения в режиме «только
пометки» до включения автозакрытия.
