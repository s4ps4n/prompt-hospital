# ТЗ: Интеграция Точка-банк → Битрикс24

**Задача:** `T-71` · зона `b24-bank` · приоритет 1

---

## Цель

Когда на расчётный счёт приходит оплата, соответствующий счёт в Битрикс24 автоматически переходит в статус «оплачен».

---

## Главное требование безопасности

**Банковские и персональные данные не покидают контур владельца.**

- **НЕ ставить** приложения из Маркетплейса B24 (First Open и подобные) — они проводят поток платежей через сервер разработчика, это утечка банковской тайны
- **НЕ отправлять** платёжные данные во внешние сервисы и LLM-шлюзы (включая Jev через `ag.omni.mice.zone`)
- **Матчинг платежа и счёта** — только локальная арифметика
- В своей системе **не хранить лишнее**: после сопоставления платёжные данные не сохраняем
- В логах — без номеров счетов, назначений и сумм

---

## Архитектура

```
Точка (вебхук о поступлении, POST + подпись JWT)
      ↓
Локальный слушатель (наш сервер):
  проверяет подпись → извлекает ИНН, сумму, назначение
  (одноразово, не сохраняет)
      ↓
Матчинг со счетами B24 (crm.invoice) по правилам ниже
      ↓
Обновление статуса счёта в B24 через API
```

**Точка — единственный внешний контур.** Никаких посредников.

---

## Статусы воронки счетов

| # | Стадия | Кто ставит |
|---|---|---|
| 1 | Новый | — |
| 2 | Авто ООО: отправка, счёт и акт | робот |
| 3 | Авто ИП | робот |
| 4 | Клиент прочитал ⚠️ | робот |
| 5 | Платёж просрочен | **робот B24** (правило 5 дней) |
| 6 | Сомнения | человек |
| 7 | Не оплачен | **человек вручную** |
| 8 | **Оплачен** | **наша система** |

**Статуса «Провален» нет** — в ранней версии ТЗ он был указан ошибочно.

**«Платёж просрочен» — не финал**, а шаг воронки.

**Задача системы:** найти счёт по платежу и перевести в «Оплачен». Больше ничего не меняем.

---

## Правила сопоставления

### В каких стадиях ищем

**Только в этих четырёх:**

| # | Стадия |
|---|---|
| 2 | Авто ООО: отправка, счёт и акт |
| 3 | Авто ИП |
| 4 | Клиент прочитал ⚠️ |
| 5 | Платёж просрочен |

**Не ищем:** Новый, Сомнения, Не оплачен, Оплачен.

**Смысл:** эти четыре — весь путь «счёт отправлен, ждём деньги». Остальное либо ещё не отправлено, либо решено человеком, либо закрыто.

### Привязка по ID, не по названию

**Ключевое требование.** Названия стадий меняются в интерфейсе B24 — `STATUS_ID` стабилен. Привязка к названию сломает интеграцию молча при любой правке воронки.

Нужно получить:
- **`STATUS_ID`** четырёх стадий из фильтра
- **`STATUS_ID`** стадии «Оплачен»
- **`entityId`** воронки счетов (вероятно `SMART_INVOICE` или `INVOICE`)

Способ: `crm.status.list` через вебхук, либо настройки воронки в интерфейсе.

### Про роботов B24

Роботы с правилом **5 дней** меняют стадию на «Платёж просрочен». **Свою логику по срокам не дублировать.**

### Уровни

| Уровень | Условие | Действие |
|---|---|---|
| **1** | ИНН + сумма = **один** счёт из четырёх стадий | ставим «Оплачен» автоматически |
| **2** | совпало **несколько** счетов | **не гадаем** → «требует проверки», показать даты и ID кандидатов |
| **3** | ничего не сошлось | список «неразобранные платежи» |

**Автозакрытие — только уровень 1.**

## Данные, нужные от владельца

1. **Токен API Точки** (JWT) — выдаётся в интернет-банке
2. **Право `ManageWebhookData`** — для подписки на вебхуки
3. **`account_id`** расчётного счёта
4. **Вебхук B24** — чтобы вытащить `STATUS_ID` стадий и `entityId` воронки
5. **Способ обновления B24:** входящий вебхук (проще) или локальное приложение (безопаснее)

---

## Приёмка

| Проверка | Ожидаемый результат |
|---|---|
| Платёж с уникальными ИНН+суммой | ровно один счёт перешёл в «оплачен», других не тронуто |
| Платёж с двумя совпадениями | **ни один** счёт не закрыт, создана пометка «требует проверки» |
| Платёж без ИНН | уровень 2 или 3, автоматики нет |
| Повторный вебхук по одному платежу | повторного закрытия не происходит (идемпотентность) |
| Логи | без номеров счетов, назначений и сумм |
| **Контроль-реверт** | убрать проверку уникальности → тест на «два совпадения» краснеет |

---

## Чего не делать

- Не ставить сторонние приложения Маркетплейса
- Не отправлять платёжные данные в LLM/Jev и любые внешние API
- Не закрывать счёт при любой неоднозначности — лучше оставить человеку
- Не хранить банковские выписки и остатки — они не нужны для задачи
