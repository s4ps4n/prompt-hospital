# Как делали: автопост и отчёты Каркаса

Автор: Гермес. Проект: `engine-autopost`.
Период: сентябрь–октябрь 2026.

## Что было (задача)

Автоматизация вокруг движка Каркас: посты в каналы, сводки разработки,
отчёты по эпикам, зеркало репозитория.

## Что сделал

**1. Хроника и анонсы.**

    хроника → @karkas_cms + чат в Битриксе, ежедневно 09:00 Улан-Удэ
    анонс   → @aiti4biz, среда 09:00 МСК (релизный выпуск для владельцев)
    /updates → страница обновлений на сайте, собирается из updates-notes.md
    зеркало  → cms_teach → engine, subtree split на каждый push

**2. Сводка разработки (ежедневно).**

Считает коммиты за сутки, закрытые и заведённые задачи, группирует
по темам из заголовков (эпики, платежи, доступность, дизайн, производительность).

**3. Отчёт по эпикам.**

Показывает прогресс эпика полоской, дельту за сутки, что закрылось
и что осталось, плюс вывод одной фразой.

## Что НЕ сработало (главное — здесь)

**1. Мёртвый токен в `git remote` → «Коммитов: 0».**

У `git remote` был вшит в URL токен `https://x-access-token:ghp_...`.
Токен отозвали, `git fetch` падал, а скрипт считал коммиты по застывшей
копии и писал «Коммитов: 0». На деле их было 15.

Формально отчёт выглядел нормально — цифра правдоподобная. Только
случайно заметили, что разработчик «ничего не делал» неделю.

**2. Протухший `GH_TOKEN` → «Эпиков: 0».**

API отдавал 401, `api()` в `except` возвращал пустой список, отчёт
печатал ноль. Та же история.

**3. Два разных `.env` — два токена.**

`daily_report.py` берёт токен из одного `.env`, `epics_daily.py` —
из другого (`GITHUB_TOKEN_PROJECTS`). Оба протухли. Чинить пришлось
в двух местах.

**4. Четыре написания пометки эпика.**

Скрипт искал `'[ЭПИК]'` в квадратных скобках. В трекере фактически:

    'ЭПИК:'    9 раз
    '[ЭПИК]'   8 раз
    '[Эпик]'   1 раз
    'Epic:'    1 раз

Итог: `epics_daily.py` видел 2 эпика из 12, а `#443 «Epic: ...»`
не видела ни одна проверка.

**5. Пять скриптов молчали так же.**

`chronicle_report`, `notify_commits`, `check_release`, `daily_chronicle`,
`dev_commits` — у всех сбой fetch или API превращался в пустой результат.
Причём поиск по `git fetch` их не находил: команда записана списком
`["git", "fetch", ...]`.

## Чем проверял

- 36 тестов: красные первыми (на старом коде падали 19 из 36);
- подставной `git origin` и подменённый GitHub — сеть не нужна;
- живая проверка: `--no-send` прогон, сверка с трекером (370 задач,
  19 эпиков — совпало);
- имитация сбоя fetch через переменные окружения git — в отчёте
  появилась причина, токен в тексте не утёк.

## Что забрать в опыт

- **Пустой результат нельзя принимать за валидный.** «Ноль коммитов»
  и «не смог получить коммиты» — разные вещи, и разница должна быть видна.
- **Токены в `.env` протухают молча.** Проверять формат и живость,
  а не наличие.
- **Формат пометок в трекере нестабилен.** Один регэксп на все написания,
  регистронезависимый, с латиницей.
- **Искать код по смыслу, а не по строке.** `["git","fetch"]` — тот же
  fetch, но поиск по тексту его пропускал.
