# Разработчик SEO Intelligence Platform

## When to Use

Есть задача в `docs/tasks/` с DoD и ссылкой на ADR. Без задачи с DoD
работа не начинается: без критерия готовности задача вернётся из приёмки,
и время уйдёт дважды.

## Предполётная проверка

Отвечать письменно, в файле задачи, до первой строчки кода. Занимает
десять минут и снимает основную причину переделок — код, написанный по
неверно понятой задаче.

1. Какие пункты ТЗ закрывает задача? Выписать номера §.
2. Какой ADR ей соответствует и что в нём решено про эту часть?
3. Какие файлы задача имеет право трогать? Выписать список.
4. Что в DoD непроверяемо? Пункт, который нельзя проверить командой или
   глазами, уточняется у архитектора сейчас, а не после сдачи.
5. Какие строки матрицы QA относятся к задаче? Открыть
   `seo-qa/references/test-matrix.md` и выписать номера. Это и есть
   критерии, по которым работу вернут — они известны заранее.
6. Какие инварианты I1–I7 задача может нарушить?
7. Чего не хватает, чтобы начать?

Если хотя бы на один вопрос ответ «разберусь по ходу» — задача не
начинается, а задаётся вопрос архитектору. Один вопрос дешевле одного
переписывания примерно на два порядка.

## Правило одного прохода

Матрица QA и чеклист приёмки лежат в репозитории и открыты. Возврат по
пункту из этих списков — не придирка проверяющего, а невыполненная
работа. Свои строки матрицы прогонять до сдачи.

| Причина переделки | Что делает её невозможной |
|---|---|
| Понял задачу иначе, чем архитектор | предполётная проверка, п. 1–3 |
| Додумал решение вместо вопроса | п. 7 — вопрос архитектору |
| Писал по памяти о структуре кода | прочитать текущие файлы перед правкой |
| Пропустил краевой случай | прогнать свои строки матрицы |
| Расширил границы задачи | список файлов из п. 3 |
| Сдал частично готовое как готовое | формат сдачи ниже |

## Procedure

1. Пройти предполётную проверку.

2. Прочитать задачу и ADR по ссылке. Не проектировать заново. Пробел в
   ADR возвращать архитектору: додуманное решение не пройдёт ревью
   критика и всё равно переделается, только позже и дороже.

3. Проверить фактическое состояние кода в границах задачи. Схема и
   структура могли измениться после того, как задача была написана.

4. Начать с тестов для детекторов и нормализации. Они спроектированы как
   чистые функции над нормализованной моделью, поэтому тестируются на
   синтетике без БД и без сети — самая дешёвая проверка в проекте.
   Минимум на детектор: срабатывание, несрабатывание, граница порога,
   пустые данные.

5. Реализовать строго в границах файлов из п. 3. Замеченное рядом
   улучшение записать отдельным предложением, а не сделать заодно.

6. Прогнать самопроверку и свои строки матрицы. Оформить сдачу.

```bash
npm test
npx tsc --noEmit
npx prisma validate

# I5: вызовы вендоров только внутри llm/providers/
grep -rE "from ['\"](openai|@anthropic-ai|@google/gener)" src --include=*.ts \
  | grep -v "^src/llm/providers/" && echo "НАРУШЕНИЕ I5"

# I4: анализ не пишет в таблицы источников
grep -rE "prisma\.(query|page|metric|goal|conversion)\.(update|delete|upsert)" \
  src/seo-analyzer src/content-planner src/llm 2>/dev/null && echo "НАРУШЕНИЕ I4"

# I6: секреты не утекают в логи
grep -rE "console\.(log|error).*(token|secret|api_?key)" src --include=*.ts \
  && echo "НАРУШЕНИЕ I6"

# I7: пороги детекторов не зашиты в код
grep -rnE "position\s*[<>=]+\s*[0-9]" src/seo-analyzer --include=*.ts \
  && echo "ПРОВЕРИТЬ I7: порог в коде вместо конфига"
```

## Формат сдачи

Без этого блока задача считается не сданной.

```text
Задача:      docs/tasks/<id>
Закрыто:     §N, §M
Не закрыто:  <пункт> — <причина>
Файлы:       <изменённые; совпадают с границами задачи>
Матрица QA:  <номера строк> — прогнал, результат
Вопросы, оставшиеся к архитектору: <или «нет»>

Вывод самопроверки:
<фактический вывод команд>
```

## Точность формулировок

- «Готово» пишется только вместе с фактическим выводом команд. Не «тесты
  проходят», а вставленный вывод.
- Ссылки на ТЗ — номерами §, на инварианты — номерами I. «Как в ТЗ» —
  не ссылка, проверить её невозможно.
- Частично сделанное называется несделанным: у DoD нет промежуточных
  состояний.
- Расхождение с задачей идёт в блок сдачи, а не остаётся молча в коде.

## Pitfalls

- **Пороги в коде.** `position >= 4 && position <= 15` внутри детектора —
  нарушение I7. Пороги приходят из конфигурации сайта, иначе система
  окажется настроенной под один сайт.

- **Ответ внешнего API без валидации.** Метрика и Вебмастер меняются;
  без zod-схемы отсутствующее поле превращается в `undefined`, потом в
  `NaN`, потом в цифру в отчёте, которой никто не поверит.

- **Деление на ноль в метриках.** Показы без кликов дают CTR 0, а не
  `NaN`. Пустой предыдущий период даёт INSUFFICIENT DATA (I2), а не
  бесконечный рост.

- **Округление.** Позиции и CTR хранятся как пришли, округляются только
  при выводе. Округлённое при записи не восстановить, а сравнение
  периодов на округлённых числах даёт ложную динамику.

- **Часовой пояс.** Границы периодов идут через одну функцию с зоной из
  конфига сайта. Локальное `new Date()` в детекторе — источник
  расхождений между отчётами.

- **UPDATE по историческим фактам.** Наблюдения append-only: Вебмастер
  пересчитывает прошлое, и перезапись убивает достоверность измерения
  результата.

- **Запись ответа LLM в источник.** Нарушение I4 даже если «модель
  исправила очевидную опечатку в запросе».

## Verification

Задача сделана, когда закрыты все пункты DoD, самопроверка чистая,
относящиеся строки матрицы прогнаны, и оформлен блок сдачи с номерами
закрытых пунктов ТЗ.
