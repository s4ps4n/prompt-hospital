# Сисадмин SEO Intelligence Platform

## When to Use

Развёртывание, миграции, расписание сборщиков, секреты, бэкапы,
мониторинг, разбор инцидента.

## Главное свойство этой системы

Исторические данные Вебмастера и Метрики доступны через API в
ограниченном окне. Если сборщик молча упал на неделю, эти данные
потеряны навсегда — их неоткуда добрать. А без непрерывной истории
статус MEASURING становится недостоверным, и главный принцип ТЗ
(измеримый результат внедрения) перестаёт выполняться.

Отсюда следует, что мониторинг сборщиков — не улучшение, а часть
требования к хранению данных. Алерт нужен не на падение задания, а на
**пропуск запуска**: упавшее задание видно, не запустившееся — нет.

## Procedure

1. **Расписание.** Сборщики по каждому источнику и сайту, с окном
   перекрытия: собирать чуть больше, чем прошло, чтобы пересчитанные
   задним числом цифры доехали как новые наблюдения.

2. **Rate limits.** У API Яндекса есть лимиты. Экспоненциальный бэкофф,
   а не повтор в цикле: цикл превращает временную ошибку в блокировку
   ключа.

3. **Секреты.** Токены в `.env` или хранилище секретов, не в образе, не в
   репозитории, не в переменных сборки CI-логов. Шифрование в покое.
   Отдельные ключи для прода и стенда: тестовый прогон, ушедший в боевой
   Вебмастер, — это WRITE в чужой сайт.

4. **Ротация OAuth.** Токены Яндекса живут ограниченное время. Алерт
   заранее, до истечения, а не после того, как сбор встал.

5. **Бэкапы Postgres.** Регулярно и с проверкой восстановления. Бэкап,
   который ни разу не восстанавливали, бэкапом не является. Проверять
   восстановление на отдельной базе по расписанию.

6. **Аудит-лог.** Все операции изменения логируются отдельно от
   прикладных логов и не ротируются вместе с ними — по §24 это
   требование, а не удобство.

7. **Миграции.** Прогон на копии боевой базы до прода. Таблицы наблюдений
   растут до десятков миллионов строк, и миграция, добавляющая индекс
   без `CONCURRENTLY`, положит сбор.

## Pitfalls

- Логи с токеном внутри — грепать перед выкладкой ротации логов наружу.
- Мониторинг только на процессе: процесс живой, задание не запускалось.
- Общий ключ API на прод и стенд.
- `pg_dump` без проверки, что дамп восстанавливается на пустой базе.
- Индекс без `CONCURRENTLY` на большой таблице в рабочее время.

## Verification

- Пропуск запланированного запуска даёт алерт (проверить, остановив
  задание намеренно).
- Восстановление из последнего бэкапа проходит на чистой базе.
- `grep` по логам и по сгенерированным отчётам не находит токенов.
- Ключи прода и стенда различаются.
