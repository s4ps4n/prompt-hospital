# Контекст проекта: SEO Intelligence Platform

## When to Use

Загружается первой в любой роли, работающей над проектом. Все остальные
скилы проекта ссылаются на инварианты отсюда по номерам (I1–I7). Если
роль не загрузила этот скил, её решения не с чем сверять.

Единственное исключение — приёмщик: он работает от текста ТЗ, а не от
внутренних договорённостей команды.

## Закон цепочки

Продукт построен вокруг одной последовательности:

```text
поисковый спрос → запрос → URL → показы/CTR/позиция → органический трафик
→ поведение → бизнес-конверсии → анализ страницы → гипотеза → SEO-задача
→ реализация → измерение результата
```

Любой объект системы обязан указывать своё место в этой цепочке. Вывод,
который не выводится из данных выше по цепочке, продуктом не является —
это мнение. ТЗ формулирует это прямо: рекомендация без подтверждающих
данных не считается задачей.

## Инварианты

Нарушение любого из них — дефект независимо от того, работает ли код.

**I1. Evidence.** Каждый Finding несёт числа, период и источник. Finding
без Evidence не сохраняется. Это то, что отличает систему от генератора
советов.

**I2. INSUFFICIENT DATA.** Когда данных не хватает, система выдаёт явный
маркер, а не осторожный вывод. «Вероятно», «похоже» и пустое место —
запрещённые исходы. Ложный вывод дороже отсутствия вывода, потому что
на его основе кто-то переделает страницу.

**I3. READ/WRITE.** Автоматически разрешено только чтение, анализ и
порождение предложений. Требуют явного подтверждения человека: изменение
сайта, создание и изменение целей Метрики, submission Sitemap, создание
файлов в рабочем проекте, commit, PR, публикация статьи, deploy.

**I4. AI не мутирует источник.** LLM читает нормализованные данные и
порождает новые объекты (Finding, ContentIdea, Brief). Запись ответа
модели обратно в Queries / Pages / Metrics — брак. Иначе через месяц
никто не сможет сказать, где измеренные данные, а где галлюцинация.

**I5. AIProvider.** Никаких вызовов конкретного вендора вне
`llm/providers/`. Интерфейс: `analyze / generate / review / classify /
cluster`. Проверка инварианта: подмена провайдера на mock не требует
правок ни в одном файле вне этой папки.

**I6. Секреты.** OAuth-токены и ключи API: не в Git, зашифрованы в
покое, не попадают в отчёты, не уходят в промпт без необходимости.
Все операции изменения логируются.

**I7. Ядро не знает про конкретный сайт.** Пороговые значения,
приоритеты, цели, кластеры — конфигурация сайта. Ни одного site-специфи-
чного условия в ядре: система должна работать на другом сайте без
переписывания.

## Словарь

**Finding** — обнаруженная проблема или возможность. Поля: ID, тип, URL,
query/кластер, priority, evidence, problem, hypothesis, recommended
action, expected KPI, confidence, status.

**Issue** — значимый Finding, взятый в работу. Статусы: `PROPOSED →
APPROVED → IMPLEMENTED → DEPLOYED → MEASURING → SUCCESS | FAILED →
REVERTED`. Переходы вне этой последовательности недопустимы.

**Snapshot** — состояние SEO на конкретную дату, восстановимое. Не копия
таблиц, а зафиксированное «что мы видели тогда».

**ContentIdea → ContentBrief** — тема статьи и полное SEO-ТЗ на неё.

**Experiment** — связка изменения и измерения результата после внедрения.

## Границы MVP

Внутри: Метрика, Вебмастер, query → URL, позиции/показы/клики/CTR,
organic landing pages, цели и конверсии, базовый техаудит, детекторы
возможностей, Findings, приоритет, поиск тем, кластеризация, контент-
план, ТЗ на статью, один AI Provider, три отчёта.

Снаружи, и появление этого в сборке — тоже дефект: Google Search
Console, Google Analytics, Ahrefs, Serpstat, Keys.so, автоматический
линкбилдинг, генерация тысяч страниц, автоматическая публикация,
автодеплой, управление рекламой, закупка ссылок.

Второй этап (не сейчас, но проектировать так, чтобы влезло): Git-интег-
рация, patches, PR, baseline до изменений, post-deploy measurement, AI
writer, AI reviewer, несколько сайтов.

## Артефакты на диске

Роль читает вход из файла и пишет выход в файл. Договорённость, которой
нет в репозитории, не существует.

```text
docs/spec/      ТЗ — вход, неизменяемый
docs/adr/       архитектурные решения + <id>.review.md от критика
docs/tasks/     задачи с DoD и границами файлов
docs/qa/        отчёты QA с воспроизведением
docs/accept/    вердикты приёмщика
prisma/, src/   код
```

## Стек и правило выбора

TypeScript, Node, PostgreSQL, Prisma.

Перед проектированием любого компонента — поиск зрелой OSS-альтернативы.
Своё пишется, только когда в ADR есть раздел, почему готовое не подошло.
Продукт этого проекта — детекторы, нормализация, приоритизация и
контент-планировщик. Всё остальное берётся готовым.
