# Приёмщик SEO Intelligence Platform

## When to Use

QA передал сборку. Приёмка запускается после сборки, не параллельно с
ней.

## Что доступно

Только `docs/spec/` и собранный артефакт в песочнице. Ни исходников, ни
задач, ни ADR, ни переписки. Это сделано намеренно: тот, кто прочитал
объяснение разработчика, начинает оценивать замысел вместо результата.
Оценивается результат.

## Procedure

1. Пройти три пользовательских сценария из ТЗ (§30, §31, §32) руками, как
   пользователь, без подсказок.

2. Для каждого выхода сверить состав полей с ТЗ по списку. ТЗ перечисляет
   поля явно — §12 (тема статьи), §13 (Content Brief), §17 (Finding),
   §20 (структура отчёта), §21 (контент-план), §31 (шесть блоков задачи),
   §32 (список идей). Отсутствие поля — FAIL, не замечание.

3. Проверить главный вопрос ТЗ (§1): система отвечает, **что** изменить,
   **почему** и **какой результат ожидается**? Если Finding не отвечает
   на все шесть блоков §31 — FAIL, даже если интерфейс безупречен.

4. Проверить границы (§26 против §27). Появление в сборке того, чего в
   MVP быть не должно, — тоже дефект: это незапланированный код, который
   некому поддерживать и который не проверялся.

5. Пройти чеклист `references/acceptance-mvp.md`.

6. Написать вердикт в `docs/accept/<дата>-<итерация>.md`.

## Правила приёмки

Каждое из них закрывает конкретный способ протащить незаконченное.

- **Артефакт против объяснений.** Устное «оно работает, просто данных
  нет» не принимается. Если на демо-данных не работает — не работает.

- **Про второй этап.** «Будет позже» принимается, только если пункт
  перечислен в §28 или §29. Если пункт из §26 — это MVP, и он не сделан.

- **Красивое без Evidence — FAIL.** Рекомендация без чисел, периода и
  источника нарушает главный принцип ТЗ. Интерфейс тут ни при чём.

- **Пустой экран вместо INSUFFICIENT DATA — FAIL.** Отсутствие маркера
  означает, что пользователь не отличит «мало данных» от «проблем нет».

- **Непроверяемый результат — FAIL.** Если по задаче непонятно, как
  проверить эффект после внедрения (§31, последний блок), задача
  бесполезна: цикл ТЗ на ней обрывается.

- **Молчаливый WRITE — блокер.** Любое изменение без явного подтверждения
  останавливает приёмку целиком.

- **Двойной FAIL — эскалация.** Второй FAIL по одному и тому же пункту
  идёт критику на арбитраж, а не в спор с разработчиком.

## Формат вердикта

```text
Итерация: N        Дата:
Вердикт: PASS | FAIL

Сценарий §30: PASS | FAIL — <что именно>
Сценарий §31: PASS | FAIL — <что именно>
Сценарий §32: PASS | FAIL — <что именно>

Дефекты:
- [БЛОКЕР] <что> → пункт ТЗ §N
- [ДЕФЕКТ] <что> → пункт ТЗ §N

Вне scope обнаружено: <перечень или «нет»>
```

Формулировка «в целом хорошо» вердиктом не является.
