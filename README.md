# Handoff: Офис оркестратора

## Overview
Изометрический мультяшный офис (стилистика ретро-симуляторов конца 90-х) — единый интерфейс управления ИИ-оркестратором: визуализация статусов моделей, приоритизация задач, drag-and-drop назначение, смена ролей, добавление/удаление моделей. Полное ТЗ — `TZ-office-visualization.md`.

## About the Design Files
`Office Orchestrator.dc.html` — **дизайн-референс в HTML**, рабочий прототип поведения и вида, а не продакшн-код. Задача — воссоздать его в целевом окружении (React/Vue/…) по принятым в кодовой базе паттернам. Если окружения нет — рекомендуется React + SVG, без внешних графических библиотек (требование ТЗ §7: оффлайн, без CDN).

Открыть прототип: положить `Office Orchestrator.dc.html` и `support.js` рядом, открыть html в браузере (нужен локальный http-сервер, напр. `npx serve`). Логика — в `<script data-dc-script>` внутри файла (класс `Component`, всё остальное — чистые функции над ним).

## Fidelity
**High-fidelity** по поведению и визуальной системе (палитра, контур, пропорции, анимации). Спрайты процедурные (SVG-полигоны), их можно переносить как есть.

## Архитектура (важно сохранить)
- **Журнал — источник истины** (ТЗ §6). Состояние `j = {workers, queue, log, seq}`; хранится в `localStorage['orch-office-journal-v1']`.
- **Все мутации — через `OPS[name](journal, args)`** (чистые функции, возвращают `{msg}` | `{err}` | `{noop}`). Обёртка `run()` клонирует журнал, применяет операцию, пишет в `log`, сохраняет. `check()` — «сухой прогон» для валидации до анимации.
- **Отрисовка — чистая функция от журнала** (`renderVals`). Сортировка очередей производная: `cmpT = priority desc, order asc`.
- Операции: `assign, reassign, unassign, setRole, setPriority, reorder, complete, block, addWorker, removeWorker, addTask`. Для боевого API оркестратора — заменить `OPS` на вызовы API с той же сигнатурой.
- **Монитор (этап B)**: `VITE_JOURNAL_URL=http://127.0.0.1:8090/journal npm run dev` (или проп `<App journalUrl=… pollMs=…/>`). Офис грузит `GET /journal` при старте и опрашивает каждые 5 с; журнал только для чтения — drag-and-drop/операции/сброс отвечают «Монитор: журнал оркестратора только для чтения». `/journal` недоступен — тихо остаётся локальный журнал (localStorage → `initial.ts`), интерактивный.

## Данные
- `worker`: `{id, model, name, provider, role, color, status: run|done|blocked|wait, task: taskId|null, doneCount, history[]}`. `w0` — Гермес (координатор, кабинет 2×2, не удаляется, роль закреплена).
- `task`: `{id, title, priority: 3|2|1, order, assignedTo: workerId|null, kind: role|null}`. `kind` — ограничение по роли (задача доступна только модели с этой ролью).
- Инвариант: `task != null` ⇔ статус `run|blocked`. Очередь модели = задачи с `assignedTo = w.id`, кроме текущей.
- `CATALOG` — 8 моделей: model, name, provider, hair, color (одежда), skin, style (прическа cap|bob|quiff|spiky|bun), acc (wings|glasses|headset).

## Правила поведения
- Drop на свободную модель → текущая задача, статус `run`. На занятую → встаёт в её очередь, текущая не прерывается.
- Drop на кабинет Гермеса или лоток → `unassign`. Drop на конверт в лотке → `reorder`: берёт приоритет цели и встаёт перед ней.
- Несовпадение `task.kind` и роли → отказ с сообщением.
- Смена роли только у свободной модели; у занятой select заблокирован, клик — тряска `nope .4s` + красная подсказка.
- Удаление — только без текущей задачи и очереди.
- «Завершить» → в history, `doneCount++`, берётся следующая из очереди по приоритету, иначе статус `done`.
- Экземпляр модели с другой ролью = новый worker того же `model`.

## Раскладка сцены (динамическая)
- Изометрия 2:1: `P(x,y,z) = [x − y, (x+y)/2 − z]`.
- Комната L=160, коридор G=110, шаг 270, поле M=55, высота стен H=64, толщина T=6. Кабинет Гермеса 2L+G.
- Сетка C колонок (prop `cols`, по умолчанию 4). Гермес занимает ячейки (0..1, 0..1); остальные заполняют построчно; при переполнении — новый ряд. Пустые ячейки ряда — зона отдыха (скамья, кулер, растения) с кнопкой «＋ свободная комната».
- Порядок отрисовки — painter's algorithm по сумме координат центра (`ox+oy+S`); персонажи в коридоре сортируются вместе с комнатами.
- Масштаб: вписать в контейнер, но не меньше 0.55 (далее скролл); вывески/конверты контр-масштабируются до ×1.5 для читаемости. Зум −/Вписать/＋.

## Персонаж (чиби)
Голова r=17 (~50% роста), белые глаза + зрачки, брови, рот по статусу, румянец, ухо; причёски и аксессуары из каталога. Сидит за столом (3/4 к зрителю), руки на клавиатуре, ЭЛТ сбоку экраном к зрителю.

## Анимации (CSS keyframes)
- run: `nod .55s` голова, `typeA/typeB .26s` руки, `pulse 1.1s` экран.
- wait: `sway 3.4s` голова ±4°. blocked: `blinkLamp .9s` красная лампа над головой, брови домиком. done: спокоен, широкая улыбка.
- `blinkEye 5s` у всех, сдвиг фазы по id.
- **Бездельники** (wait/done, кроме Гермеса) по своему графику (~45 с на занятие, со сдвигом по id) выбирают одно из: **гуляет** по коридору перед комнатой (`walkLane 11s` через CSS-переменные `--x0/--y0/--x1/--y1`, разворот `face`, шаги `stepA/B .45s`), **пьёт кофе** у двери (`sip 4s`, пар `steam 1.6s`), **спит на клавиатуре** (голова на столе, `zfloat` «z z z», слюна `drool`). Смена позы — `fadeIn .9s`. Пока гуляет/пьёт кофе — кресло пустое. На гуляющего можно кликать и бросать задачи.
- Полёт конверта после drop: 450 мс, left `cubic-bezier(.4,0,.2,1)`, top `cubic-bezier(.3,-.6,.6,1)` (дуга); операция применяется по приземлении.
- prop `motion=false` отключает все анимации.

## Экран
Верх: название, счётчики статусов, ＋Модель, зум, Журнал (JSON-дамп), Сброс. Слева: «Лоток Гермеса» (250px) — список конвертов с ▲▼, форма новой задачи (название, приоритет, роль). Центр: сцена. Справа (по клику на комнату, 290px): карточка — аватар, провайдер, статус, роль, текущая задача (Завершить / Блок / В лоток), очередь модели (▲▼↩), выполнено + история, «＋ Экземпляр с другой ролью», «Убрать из офиса». Модалка каталога: сетка моделей + роль. Низ: строка сообщений/ошибок. На узком экране колонки переносятся (flex-wrap).

## Drag-and-drop
Pointer events (мышь + тач, `touch-action:none`), порог 5px (иначе клик). Цель — `elementFromPoint` → ближайший `[data-drop]` (id worker'а или `queue`) и `[data-task-slot]` для перестановки. Призрак следует за курсором; подсветка цели — жёлтая заливка пола и красная рамка вывески/лотка.

# Prompt Hospital — план работ и состав команды

## Документы

- `TZ.md` — ТЗ на реализацию (стек, объём, критерии).
- `docs/handoff/README.md` — спека дизайнера (источник истины по поведению и виду).
- `docs/handoff/Office Orchestrator.dc.html` + `support.js` — high-fidelity референс.

## Состав команды (кто реально работает)

| Исполнитель | Офис-роль | Задачи в проекте |
|---|---|---|
| **Гермес (DeepSeek)** | координатор | декомпозиция, распределение, приёмка, контроль-реверты, ревью, интеграция |
| **Claude Code (Anthropic)** | фулстак | ядро: журнал + операции (этап 1), изометрия, drag-and-drop |
| **Codex (OpenAI)** | фулстак №2 | персонажи/спрайты, анимации, полировка — параллельно Клоду. Статус: установлен, ждёт OAuth (`codex login`) |
| **Бесплатные (OpenRouter `:free`)** | рецензент/генератор | второе мнение на код, генерация спрайтов/палитры/тестовых данных |

**Роли** (режимы работы, не отдельные API): архитектор, UX/UI, приёмщик — исполняются
Гермесом или делегируются Claude Code / Codex.

**Разделение по исполнителям:**
- **Claude Code** — глубокая работа с файлами и логикой (журнал, операции, изометрия, интерактив).
- **Codex** — параллельный код-агент (спрайты, анимации, полировка) — второй поток, чтобы
  не упираться в одного исполнителя.
- **Бесплатные OpenRouter-модели** — не агенты с файловой системой, а API-вызовы: ревью
  кода, «второе мнение», генерация SVG-спрайтов и тестовых данных по спеке. Я даю контекст
  файлом, забираю ответ.
- **Гермес** — никто не сливает результаты в main без приёмки.

Важно: в визуализации офиса модели (Claude, Codex/GPT, Gemini, Qwen, Mistral, Grok, Llama)
фигурируют как «работники» — это данность интерфейса и одновременно зеркало реального
распределения задач. Реально исполняют работу перечисленные выше движки.

## План работ (8 этапов)

### Этап 0 — Каркас проекта
Vite + React + TypeScript, линт/форматтер, `.gitignore`, структура каталогов, статическая
сборка без CDN. Итог: пустое приложение собирается оффлайн.

### Этап 1 — Журнал и операции (ядро)
`journal` + `OPS` (assign/reassign/unassign/setRole/setPriority/reorder/complete/block/
addWorker/removeWorker/addTask), обёртка `run()`, `check()`, инварианты. **Unit-тесты на
каждую операцию** (это фундамент — от него зависит всё остальное).

### Этап 2 — Изометрическая сцена
Раскладка (сетка, кабинет Гермеса 2×2, коридор, зона отдыха), painter's algorithm, комнаты,
ковры по ролям, внешние стены, пол коридора, трава.

### Этап 3 — Персонажи и статусы
Чиби-персонажи (голова/глаза/брови/рот/румянец, причёски cap|bob|quiff|spiky|bun, аксессуары
wings|glasses|headset), ЭЛТ-мониторы, экраны по статусу, вывески с лампочкой.

### Этап 4 — Интерактив
Drag-and-drop (мышь, порог 5px, призрак, подсветка цели), лоток Гермеса (список, ▲▼,
форма новой задачи), карточка персонажа (Завершить/Блок/В лоток, очередь, история,
«＋ экземпляр», «Убрать»), каталог моделей, смена роли.

### Этап 5 — Анимации
Статусные (nod/type/pulse/blinkLamp/blinkEye) + idle-бездельники (гуляет по коридору,
пьёт кофе, спит на клавиатуре) + полёт конверта + `nope` + `motion=false`.

### Этап 6 — Приоритизация и очереди
Флажки приоритета, сортировка очередей (`priority desc, order asc`), reorder перетаскиванием,
`task.kind` — ограничение по роли.

### Этап 7 — Полировка
Зум −/Вписать/＋, контр-масштаб вывесок/конвертов, производительность
(много workers), сброс, JSON-дамп журнала.

### Этап 8 — Приёмка
Прогон по критериям `TZ.md §7` + контроль-реверты (сломать инвариант → тест красный),
сверка с референсом дизайнера. Демо Дмитрию.

## Порядок и правила

- Каждый этап — отдельная ветка; коммит только когда тесты зелёные.
- Контроль-реверт обязателен для операций журнала (этап 1) и drag-and-drop (этап 4).
- Приёмку каждого этапа делает Гермес (не сам исполнитель).
- Работа **не начинается до согласования** этого плана Дмитрием.
