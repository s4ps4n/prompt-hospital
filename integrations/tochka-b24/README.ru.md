# Точка → Битрикс24: счёт → «Оплачен»

Реализация ТЗ T-71 v3 (`docs/tasks/TZ-B24-TOCHKA-INTEGRATION-v3.md`). Поступление на р/с в Точке переводит
счёт Б24 в «Оплачен» — **только** при однозначном совпадении ИНН плательщика и суммы (до копейки).
Всё неоднозначное уходит человеку.

```
Точка ──POST JWT(RS256)──▶ слушатель 127.0.0.1 (за Traefik, HTTPS)
                              │ подпись по JWKS Точки (iss/aud/exp) → 401 | 200 сразу
                              ▼
                           очередь (in-process, последовательная)
                              ▼
                           матчинг — локальная арифметика (src/matcher.ts)
                              ▼
                           Б24 владельца через локальное приложение (OAuth)
                              ▼
                           журнал идемпотентности (единственное хранилище)
Раз в сутки: выписка Точки за вчера–сегодня → тот же матчинг и журнал; проверка подписки на вебхук.
```

Внешних адресов три: Точка (вебхуки, JWKS, выписка, подписка), портал Б24 владельца и сервер авторизации
Б24 `oauth.bitrix.info` (только обмен токенов, платёжных данных там нет). Нет Маркетплейса, нет LLM/Jev,
нет сторонних API, нет npm-зависимостей в рантайме (Node ≥ 22.18).

## Правила

Ищем **только** в стадиях `B24_SEARCH_STAGES` («счёт отправлен, ждём деньги»). Система меняет только одно —
ставит `B24_PAID_STAGE`. «Новый», «Сомнения», «Не оплачен», «Оплачен» в поиск не входят; «Платёж просрочен»
входит (его ставит робот Б24 — сроки сервис не считает).

| Уровень | Условие | Действие |
|---|---|---|
| 1 | ИНН + сумма → ровно **один** счёт | перепроверка стадии → «Оплачен» + дата оплаты + комментарий «оплачен автоматически по платежу <operationId>» |
| 2 | несколько счетов с ИНН+суммой · сумма = сумме 2+ счетов ИНН · частичная · переплата · ИНН нет, совпала только сумма (≤ 5 счетов) | стадию **не меняем**; флаг (если задан `B24_REVIEW_FIELD`) + комментарий в таймлайн **каждого** кандидата: случай, данные платежа, кандидаты с датами выставления и стадиями; задача ответственному (срок — сегодня, ссылки на кандидатов); одно сообщение ответственному |
| 3 | ИНН нет и сумма не совпала · у ИНН нет счетов в стадиях поиска · > 5 совпадений только по сумме | задача ответственному, срок — сегодня: сумма, ИНН, назначение, дата, operationId; одно сообщение |

Назначение платежа — только подсказка («упомянут в назначении»), уровень не повышает.
ИНН проверяется по контрольной сумме; мусор и нули = «ИНН нет».

**Привязка — только по `STATUS_ID`.** Таблица стадий в ТЗ (§3а) — описание для читателя, не конфиг: номеров и
названий стадий в коде нет. Фильтр применяется дважды (в запросе к Б24 и локально); новая стадия воронки в
поиск сама не попадает.

## Данные и логи

- Платёж живёт только в памяти на время обработки. На диске — журнал: `HMAC(operationId) → { invoiceId, result, at }`,
  90 дней. Сумм, ИНН, назначений, выписок нет.
- Лог (stdout, JSON) — только `event/ref/level/reason/candidates/status/error`. Проверяется тестом.
- Данные платежа видит только владелец — в своей CRM (комментарий/задача).

## Надёжность

- 200 уходит Точке до обработки. Сбой Б24 → платёж не пишется в журнал → его подберёт повторная доставка
  или ежедневная сверка.
- Повтор по `operationId` — пропуск. Счёт уже «Оплачен» — вне поиска, второй раз не закроется.
- Страховка на случай, если ключ операции в выписке не совпадёт с ключом вебхука: в записи журнала есть `fp` =
  HMAC(юрлицо|ИНН|сумма). Если такой отпечаток уже встречался за последние 3 дня, уровень 1 не закрывает счёт, а
  отправляет его на проверку («возможный повтор»). Иначе тот же платёж под другим ключом закрыл бы следующий счёт
  клиента на ту же сумму. Цена: две настоящие оплаты одной суммы от одного ИНН за 3 дня — вторая уйдёт человеку.
- 5 отказов подписи подряд, недоступность Точки при сверке, слетевшая подписка → сообщение ответственному в Б24.

## Эндпоинты (на `PUBLIC_BASE_URL`, через Traefik)

| Путь | Назначение |
|---|---|
| `POST /webhook/tochka` | вебхук Точки: тело — строка JWT (`text/plain`), RS256 по `TOCHKA_JWK_FILE` → 401 или 200 сразу |
| `GET /oauth/tochka/start?key=…&org=ooo\|ip` | подключить приложение Точки юрлица (своё у ООО и у ИП) |
| `GET /oauth/tochka/callback` | redirect_uri Точки (`TOCHKA_REDIRECT_URL`); юрлицо — из одноразового state |
| `POST /oauth/b24/install?key=…` | путь установки локального приложения Б24 |
| `GET/POST /handler` | путь обработчика приложения Б24 (обмен code, страница статуса) |
| `GET /healthz` | живость |

`/oauth/*` и `/handler` работают, только если задан `OAUTH_SETUP_KEY`.

## Юрлица

ООО и ИП — два приложения Точки: `TOCHKA_OOO_*` и `TOCHKA_IP_*` (`CLIENT_ID`, `CLIENT_SECRET`, `ACCOUNT_ID`, `NAME`,
`B24_MYCOMPANY_ID`). Платёж ищется среди счетов того юрлица («Моя компания» счёта), на чей р/с пришли деньги;
совпадение со счётом другого юрлица — уровень 2 «другое юрлицо». Сверка и проверка подписки — по каждому приложению.

## Установка

1. **Б24, локальное приложение** (серверное), права `crm`, `task`, `im`; путь обработчика `https://it-uu.ru/handler`,
   путь установки `https://it-uu.ru/oauth/b24/install?key=<OAUTH_SETUP_KEY>`. `client_id/secret` → `.env`.
   Токены — при установке, либо `/oauth/b24/start?key=…`, либо вручную `node --env-file=.env src/b24-auth.ts <code>`.
2. **ID с портала:** `node --env-file=.env src/stages.ts` (список смарт-процессов) →
   `node --env-file=.env src/stages.ts <entityTypeId>` (воронки и `STATUS_ID`). Заполнить `B24_ENTITY_TYPE_ID`,
   `B24_CATEGORY_ID`, `B24_PAID_STAGE`, `B24_SEARCH_STAGES`. Сервис не стартует, если список пуст или в нём «Оплачен».
3. `cp .env.example .env`, заполнить, `JOURNAL_SECRET=$(openssl rand -hex 32)`.
4. Запуск: `node --env-file=.env src/server.ts`; `WEBHOOK_PATH` опубликовать через Traefik (HTTPS).
5. Точка: `/oauth/tochka/start?key=…&org=ooo`, затем `&org=ip` — вход владельца в каждое юрлицо.
6. Подписка на вебхук: URL `PUBLIC_WEBHOOK_URL` (по умолчанию `https://it-uu.ru/webhook/tochka`) передать персональному
   менеджеру Точки — это действие владельца. `node --env-file=.env src/subscribe.ts` пробует подписать через API и
   показывает статус по каждому юрлицу; дальше подписку проверяет сверка.

**Внедрение:** песочница Точки + тестовый портал → неделя на бою с `AUTO_CLOSE=false` («только пометки»:
уровень 1 пишет в таймлайн, но не закрывает) → `AUTO_CLOSE=true`.

## Проверить на песочнице (в тестах не проверено — нужны реальные ответы)

- Ключ: `node --env-file=.env src/check-key.ts [файл с телом вебхука]` — от пользователя, которому доступен
  `TOCHKA_JWK_FILE` (права 600). Показывает тип и длину ключа, сверяет его с опубликованным JWKS Точки по отпечатку.
  Если передан файл с настоящим вебхуком, проверяет подпись и печатает имена полей, `iss` и `aud`, но не сами данные.
  Код возврата 0 — всё в порядке.
- `iss`/`aud` вебхука Точки → `TOCHKA_JWT_ISS`/`TOCHKA_JWT_AUD` (пока не заданы — сервис пишет предупреждение в лог).
- Имена полей вебхука (`operationId`/`paymentId`, `SidePayer.inn`, `SideRecipient.account/bankCode`, `amount`) и выписки
  (`Transaction[].creditDebitIndicator`, `Amount`, `DebtorParty.inn`). **Главное:** ключ операции в выписке должен
  совпадать с ключом вебхука, иначе сверка обработает платёж повторно (закрыть второй раз не сможет, но будет лишняя пометка).
- `ENTITY_TYPE` таймлайна для счёта (`smart_invoice` / `dynamic_<id>`) и срабатывание `im.notify.system.add`.

## Тесты

`npm test` из этой папки — матчер, журнал, сверка, JWKS, OAuth (в т. ч. разбор callback Точки: успех, ошибка
провайдера, чужой `client_id`) и сквозной сценарий (подписанный JWT → HTTP → очередь → фейковый REST Б24).
`test/b24.test.ts` — клиент Б24 против подставного портала (локальный HTTP): каждый вызов REST (`crm.item.list`,
`crm.requisite.list`, `crm.status.list`, `crm.item.get`, `crm.item.update`, `crm.timeline.comment.add`,
`tasks.task.add`, `im.*`) проверяется по методу и телу запроса; STATUS_ID — только из конфига.

**Тип счетов** — смарт-процесс «Счета» (`crm.item`, `entityTypeId 31`): с 2022 г. новые счета Б24 — только он;
старые `crm.invoice.*` устарели и не имеют стадий `DT31_<воронка>:…`, на которых построен поиск. На конкретном
портале подтвердить `node --env-file=.env src/stages.ts` (список смарт-процессов и стадий).
Временные файлы тестов — в `./.tmp` (в `.gitignore`), не в системном `/tmp`.

Callback Точки: юрлицо определяется по одноразовому `state`; если Точка передала `client_id`, он обязан быть
приложением этого юрлица, иначе 403 без обмена кода. `?error=…` от Точки → 400, текст ошибки в лог не пишется.
