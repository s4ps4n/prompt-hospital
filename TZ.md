# ТЗ: реализация «Prompt Hospital»

## 1. Исходное положение

Есть два документа — читать в этом порядке:

1. **`docs/handoff/README.md`** — спека дизайнера (архитектура, данные, правила поведения,
   раскладка, визуальная система, персонаж, анимации, экран, drag-and-drop). **Это источник
   истины по поведению и виду.**
2. **`docs/handoff/TZ-office-visualization.md`** — исходное ТЗ (цель, три функции, критерии).

Плюс **`docs/handoff/Office Orchestrator.dc.html`** + `support.js` — high-fidelity референс:
рабочий прототип поведения и вида, **не продакшн-код**.

## 2. Задача

Воссоздать референс дизайнера как **продакшн-приложение** по спеке README. Не «с нуля» и не
«скопировать HTML как есть» — перенести логику и визуальную систему в чистое, расширяемое
приложение по принятым паттернам.

## 3. Цель (напоминание, из исходного ТЗ)

Единый интерфейс управления ИИ-оркестратором:

1. **Визуализация работы** — кто из моделей чем занят, статусы.
2. **Приоритизация задач** — приоритет, сортировка очередей.
3. **Управление составом моделей** — добавлять/убирать модели, менять роли.

## 4. Технические решения

- **Стек:** Vite + React + TypeScript + SVG. Без внешних графических библиотек (Three.js,
  D3, canvas-фреймворки — запрещены). Спрайты — процедурные SVG-полигоны, переносятся из
  референса.
- **Сборка:** статический бандл Vite. Итог — самодостаточный набор файлов, открывается
  оффлайн (`file://` или локальный статик-сервер), без CDN, без сети.
- **Журнал — источник истины:** `localStorage['orch-office-journal-v1']`, структура
  `{workers, queue, log, seq}` (см. README §Архитектура).
- **Все мутации — через `OPS[name](journal, args)`** — чистые функции, возвращают
  `{msg}|{err}|{noop}`. Обёртка `run()` клонирует журнал → применяет операцию → пишет в log →
  сохраняет. `check()` — сухой прогон для валидации до анимации.
- **Отрисовка — чистая функция от журнала.** Нет состояния в DOM. Сортировка очередей
  производная (`priority desc, order asc`).
- **Инвариант:** `task != null` ⇔ статус `run|blocked`. Очередь модели = задачи с
  `assignedTo = w.id`, кроме текущей.

## 5. Функциональный объём (по README, не расширять)

- Операции: `assign, reassign, unassign, setRole, setPriority, reorder, complete, block,
  addWorker, removeWorker, addTask`.
- Drop на свободную → `run`; на занятую → в очередь; на Гермеса/лоток → `unassign`;
  на конверт в лотке → `reorder` по приоритету.
- `task.kind` — ограничение по роли; несовпадение → отказ с сообщением.
- Смена роли — только у свободной модели; у занятой select заблокирован + тряска `nope` + подсказка.
- Удаление — только без текущей задачи и очереди.
- «Завершить» → в history, `doneCount++`, берётся следующая из очереди.
- Экземпляр модели с другой ролью = новый worker того же `model`.

## 6. Раскладка (динамическая, по README)

- Изометрия 2:1 `P(x,y,z)=[x−y,(x+y)/2−z]`; комната L=160, коридор G=110, шаг 270, стены H=64.
- Кабинет Гермеса 2L+G (ячейки 0..1,0..1). Остальные заполняют сетку построчно (cols=4);
  переполнение → новый ряд; пустые ячейки — зона отдыха с кнопкой «＋ свободная комната».
- Painter's algorithm по `ox+oy+S`. Масштаб вписать, минимум 0.55; вывески/конверты
  контр-масштаб ×1.5.

## 7. Критерии приёмки (из исходного ТЗ §8 + README)

- Открывается оффлайн, узнаётся ретро-симулятор, 4 статуса видны сразу, анимация плавная.
- Drag-and-drop: на свободную → печатает; на занятую → очередь (не прерывается);
  на Гермеса → возврат; на конверт → reorder.
- Смена роли у свободной работает, у занятой — блок + тряска.
- Добавление/удаление модели, приоритизация, «＋ экземпляр с другой ролью».
- Действия переживают перезагрузку (localStorage).
- Без ошибок консоли, без разъехавшихся объектов, адаптив (flex-wrap), зум.
- `motion=false` отключает анимации (для тестов и слабых машин).

## 8. Границы

- Не подключать реальный оркестратор/API — только локальный журнал + localStorage.
- Не делать 3D/WebGL, не тянуть CDN, не менять визуальную систему дизайнера.
- Боевой API оркестратора — замена `OPS` на вызовы API с той же сигнатурой (отложено).
